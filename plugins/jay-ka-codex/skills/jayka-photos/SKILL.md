# JayKA · Photos

Recipe so that the photos users upload (of a shop, a product, a profile) **weigh little, look good, are not a risk and can be identified**. The numbers are defaults; change them in **My settings**.

## Arguments
Received: the text accompanying the skill invocation in the user message · Conventions: `../jayka-working-rules/reference/conventions.md` (path relative to this skill).
Any other argument: answer only «Unknown argument `<argument>`. Options: …» with the options of this table, and do nothing else.

| Argument | What it does |
|---|---|
| *(empty)* | **Default.** Starts at step 1 with all its questions |
| `<which photos>` | Free text (for example «cover and logo of the shop, product photos»). It answers the first question of step 1; the others are asked |

## Defaults
| Parameter | Value |
|---|---|
| Maximum upload size | **5 MB** |
| Accepted types (by content) | JPG, PNG, WebP |
| Maximum long side | **1200 px** (a small photo is never enlarged) |
| Stored format | **WebP** |
| Quality | 82, going down by 6 to 60 if it exceeds ~220 KB |
| Name | `img-<owner>-<role>[-<item>].webp` |

## Rules
1. **Permissions:** installing an image library (for example `sharp` in Node, or `Pillow` in Python) requires permission. In Laravel the **GD** extension that comes with PHP is used; check that it has WebP (`function_exists('imagewebp')`) before starting.
2. **Nothing from the client is believed:** extension and declared type are worthless. The type is detected **by the content** of the file.
3. **It is always re-encoded.** That discards metadata (location, camera) and hidden payloads.
4. The file name is **generated by the server**, never the one the user brings.
5. The database stores **only the relative path**, not the full address.
6. A new file **replaces** the previous one and the old one is deleted (no orphans).
7. Private keys and paths are not mixed with public ones: catalog photos go in public storage; people's documents in private storage with authenticated download.

## Steps of the recipe
1. **Ask** (short): which photos are uploaded (cover, logo, product, profile)? Who uploads them (the owner, an administrator, both)? Hosting and available image library? Values different from the defaults?
2. **Storage:** public folder per owner (`<owners>/<id>/…`) and public link (in Laravel, `php artisan storage:link`, which requires permission if it creates links). Confirm that the web server serves that folder.
3. **Photo service** (a single class/module with all the rules): validates size and type, straightens by EXIF, reduces, compresses, saves with a clear name, updates the database, deletes the previous one. Reference code (Laravel + GD) in `reference/laravel-gd.md`; interface ideas and tests in `reference/client-snippets.md`.
4. **Names:** `img-<owner>-cover.webp`, `img-<owner>-logo.webp`, `products/img-<owner>-menu-<product>.webp`. No accents or spaces (convert them with a «slug»). If two items of the same owner have the same name, the second one carries its number so they do not overwrite each other.
5. **Cache version:** when showing the photo, add `?v=<file modification date>` so a change shows at once. If the file does not exist, use a fallback image.
6. **Endpoints:** upload by multipart `POST` with CSRF, protected by session and by **ownership** (an owner only uploads to their own). Responses with the same business error format as the project (`photo_too_large`, `photo_format`, `photo_missing`…).
7. **Interface:**
   - A «Change photo» button that opens the picker, checks the size in the browser (clear message if over 5 MB) and **submits by itself** on choosing.
   - Shows the current photo, the help text («JPG, PNG or WebP, up to 5 MB. It is compressed automatically.») and the server errors.
   - On the web with nested forms: the file field is tied to a separate form with the `form` attribute.
   - If the admin panel also uploads photos (on behalf of the owner): same service, it goes in the log and the current file can be **downloaded** to share it.
8. **PHP (or server) limits:** `upload_max_filesize` and `post_max_size` must be **greater** than the maximum (for example 6 M and 8 M). If not, the server rejects the file before it reaches the code and the user sees a confusing error. Locally, with PHP's built-in server, they can go in a separate `.ini` loaded with `PHP_INI_SCAN_DIR`. On the hosting, in `php.ini` or the panel. Also check the proxy or web server limit (`client_max_body_size` in Nginx).
9. **Sample data:** sample photos go through **the same service** (same rules and names) so that what is seeded looks the same as what is uploaded.
10. **Tests** (one per rule): big photo → reduced to 1200 px with proportions intact; small photo → not enlarged; replacement → deletes the previous one; more than 5 MB → error `photo_too_large`; PDF with an image extension → error `photo_format`; no file → `photo_missing`; someone else's resource → 404; no session → 401.
11. **Verify in the browser:** upload a real photo from mobile and from desktop, see that it loads without breaking, and check the final size (most real photos end up between 40 and 250 KB).

## What NOT to do
- Do not keep the original without re-encoding «just in case».
- Do not rely on `accept="image/*"` as a defense: it is only convenience.
- Do not expose private folders through the same public link.
- Do not commit clients' real test photos to a repository.

## Done when
- All the rules live in a single photo service.
- The step 10 tests exist and pass (real output in the summary).
- The server limits are **measured** (for example `php -i` filtering `upload_max_filesize` and `post_max_size`) and are greater than the upload maximum.
- A real upload, done from the browser on mobile and on desktop, gave a `.webp` with a long side of 1200 px or less, the name following the convention, and a size noted in the summary.
